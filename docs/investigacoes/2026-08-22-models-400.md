# Investigação — HTTP 400 em `GET /v1/providers/{id}/models`

> Material da sessão de execução da Fase U2 (#144/#145), a pedido do owner.
> Achado original: 7 requisições com status 400 no console do navegador durante o E2E
> `onboarding-chat.spec.ts`, todas para `http://127.0.0.1:1423/v1/providers/<uuid>/models`.

## 1. Sintoma

Durante o fluxo e2e (e qualquer sessão real cujo provedor esteja inalcançável), o shell dispara
`GET /v1/providers/{id}/models` e recebe **400** repetidamente (1× por montagem/troca de provedor).
O frontend engole com `.catch(() => undefined)` (`src/app/WorkspaceShell.tsx`, efeito de modelos),
então não há quebra funcional — apenas ruído de rede/console e um erro real mascarado como 400.

## 2. Cadeia de chamadas

```
WorkspaceShell (useEffect em activeProvider)
  → listStoredProviderModels(providerId)            src/shared/api/sidecar.ts
    → GET /v1/providers/{id}/models                 sidecar/src/index.ts:485-491
      → listStoredProviderModels(id)                sidecar/src/providers.ts:805
        → getProvider(id)                           ok (provedor existe)
        → listProviderModels(...)                   providers.ts:685
          → OpenAIAdapter.listModels()              providers.ts:325
            → GET {baseUrl}/models   ← FETCH REAL PARA A REDE
```

## 3. Causa raiz (três camadas)

1. **O mock do e2e não cobre listagem de modelos.** `BLACKWALL_E2E_MOCK=1` só curto-circuita
   `validateProvider` (`sidecar/src/providers.ts:574`). O mock da conversa vive na camada de
   *streaming* (`scriptedHarnessTurn`), não no adapter HTTP. Logo, `listModels` faz fetch real
   para `http://127.0.0.1:17999/v1/models` — **porta onde nada está escutando** no ambiente e2e.
2. **Falha de rede vira exceção genérica.** `request()` encapsula qualquer falha de fetch em
   `ProviderConnectionError` (`providers.ts:276-284`); a mensagem amigável seria "Não foi possível
   listar os modelos…".
3. **O handler local mapeia QUALQUER exceção para 400.** O catch-all do roteador HTTP local faz
   `writeJson(response, 400, { error: message })` para todo erro (`sidecar/src/index.ts:662-666`),
   sem distinção entre conexão recusada, 404 de provedor ou erro interno. Por isso o navegador vê
   400 mesmo para "conexão recusada".

## 4. Observação adicional (contrato)

Apesar do nome, `listStoredProviderModels` **não lê só o SQLite**: ela lista modelos ao vivo do
endpoint remoto e apenas *mescla* metadados persistidos por cima (`providers.ts:805-856`). Com
provedor offline, nem os modelos já sincronizados no banco são retornados — o shell então cai no
fallback `[selectedProviderModel]`. Nome e comportamento divergem; vale decisão de contrato.

## 5. Opções de correção (para Issue própria)

| Opção | Escopo | Prós | Contras |
|---|---|---|---|
| **A. Stub no mock e2e**: servir `{data:[...]}` em `/models` quando `BLACKWALL_E2E_MOCK=1` (ou pular `listStoredProviderModels` sob o flag, como já ocorre em `validateProvider`) | e2e only | Elimina o ruído nos testes; zero risco de produto | Não corrige produção |
| **B. Fallback local**: em caso de `ProviderConnectionError`, retornar os modelos do SQLite (`available = 1`) antes de falhar | produto | Provedor offline continua utilizável; mata o sintoma raiz | Muda comportamento documentado; precisa de teste |
| **C. Mapeamento de status no catch-all**: `ProviderConnectionError→503`, `not found→404`, resto `500`; 400 só para entrada inválida | produto | Erros honestos; frontend pode diferenciar | Toca contrato consumido por vários painéis |

Recomendação: **A + C** (A destrava o ruído imediato do e2e; C é o conserto estrutural). B fica
como melhoria separada, pois altera UX offline de propósito.
